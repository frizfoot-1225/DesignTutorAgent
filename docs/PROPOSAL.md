## 0. 이 문서의 사용 방법

너는 이 제안서를 받은 개발 담당자다. 아래 순서로 진행한다.

1. 제안서 전체를 읽고, 이해한 내용과 구현 계획(Phase별 산출물, 예상 파일 구조, 궁금한 점)을 먼저 정리해서 보여준다.
2. 내가 승인하면 Phase 0부터 순서대로 구현한다.
3. Phase 하나가 끝날 때마다 멈추고 보고한다(10장 보고 형식 참고). 승인 없이 다음 Phase로 넘어가지 않는다.
4. 불명확한 부분은 추측하지 말고 질문한다.

## 1. 과제 배경 및 목표

### 1.1 배경
- 메모리(DRAM/NAND) 설계 부서에 배치된 신입·전배·비전공 인력이 실무에 투입되기까지 시간이 오래 걸린다.
- 메모리 설계는 일반 디지털(ASIC) 설계와 달리 셀 어레이, 센스앰프, 타이밍 파라미터, 공정 연계 등 고유 지식이 많은데 이를 체계적으로 배울 수 있는 교재가 부족하다.
- 기초 질문이 선배 엔지니어에게 집중되어 교육 부담이 크다.

### 1.2 목표
- 메모리 설계 전체 Flow(스펙 → 아키텍처 → 회로 → 시뮬레이션 → 레이아웃 → 검증 → 테이프아웃 → 테스트/양산)를 **쉽게 배우고**, 실무 문서를 읽고 설계 리뷰에 참여할 수 있는 **실무 적응 수준**까지 끌어올리는 AI 튜터를 만든다.
- 사내 과제 시연용 프로토타입이지만, 나중에 사내 LLM과 사내 문서로 교체할 수 있는 구조로 만든다.

### 1.3 성공 기준
- 신입이 설계 Flow의 각 단계가 무엇을 하는지, 자기 업무가 어느 단계인지 설명할 수 있다.
- 주요 타이밍 파라미터(tRCD, tRP 등)가 회로의 어느 부분에서 결정되는지 연결해서 설명할 수 있다.
- 간단한 회로/디지털 실습을 스스로 돌리고 결과를 해석할 수 있다.
- 실무 케이스(예: 특정 뱅크 읽기 페일)를 보고 원인 후보와 확인 절차를 말할 수 있다.

## 2. 대상 및 범위

- **대상:** 메모리 설계 부서 신입·전배 엔지니어, 비전공 출신 설계 인력
- **1차 범위:** DRAM 중심. NAND는 기초 개념과 DRAM과의 비교 수준까지만 다룬다.
- **제외:** 실제 제품 설계 데이터, 공정 파라미터, 사내 대외비 자료. 모든 학습 자료는 공개 지식(교과서, 논문, JEDEC 공개 규격 수준)으로만 작성한다.

## 3. 학습 콘텐츠 설계 (가장 중요)

### 3.1 커리큘럼 구조 (Level 1 → 4)

**Level 1 — 메모리 기초**
- 메모리 종류와 위치(SRAM/DRAM/NAND/신메모리, 메모리 계층)
- DRAM 셀(1T1C) 구조와 동작, 커패시터에 전하가 저장되는 원리, 리프레시가 필요한 이유
- NAND 셀(플로팅게이트/차지트랩), 3D NAND 구조, 프로그램/이레이즈/리드
- 어레이 구조: 뱅크, 매트, 서브어레이, 워드라인/비트라인, 페이지/블록(NAND)
- 기본 동작 시퀀스: ACT → RD/WR → PRE, 리프레시; NAND 프로그램/리드 시퀀스
- 필수 용어와 약어

**Level 2 — 설계 Flow 이해**
각 단계마다 목적, 입력/출력, 담당 역할, 사용 툴 종류, 산출물, 흔한 문제를 정리한다.
1. 제품 스펙 및 표준 분석 — JEDEC 규격(DDR5, LPDDR5, HBM), NAND 인터페이스(ONFI/Toggle), 스펙 읽는 법
2. 아키텍처 설계 — 어레이 구성, 대역폭·전력 목표, 리던던시, 다이 사이즈 추정
3. 회로 설계
   - 코어: 셀, 센스앰프, 서브워드라인 드라이버, 비트라인 프리차지/이퀄라이즈
   - 주변: 로우/컬럼 디코더, I/O 회로, DLL/PLL, 차지펌프, 내부전압 생성기
   - 디지털 제어: 커맨드 디코더, 모드 레지스터, 리프레시 카운터, ECC, DFT/BIST
4. 시뮬레이션 — SPICE, PVT 코너, 몬테카를로, 센싱 마진 분석
5. 레이아웃 및 물리 검증 — 커스텀 레이아웃, DRC/LVS, RC 추출, 포스트 레이아웃 시뮬레이션
6. 검증 — 기능 검증, 타이밍 검증, IR drop/EM, ESD, 신뢰성
7. 테이프아웃 이후 — 웨이퍼 테스트, 특성 평가(characterization), 불량 분석(FA), 수율 램프, 설계 피드백

**Level 3 — 핵심 파라미터와 회로의 연결**
- DRAM 타이밍: tRCD, tRP, tRAS, tRC, tCL, tWR, tRFC, tREFI, tRRD, tFAW
- NAND: tPROG, tR, tBERS, 리텐션, 인듀어런스
- 각 파라미터가 어떤 회로 블록과 물리 현상(비트라인 캡, 셀 캡, 센스앰프 오프셋, 워드라인 RC 등)에 의해 결정되는지 매핑 표로 정리
- 전력/노이즈 항목: 액티브 전력, 리프레시 전력, 전원 노이즈, 커플링

**Level 4 — 실무 적응**
- 스펙 해석 훈련: 타이밍 표와 다이어그램을 보고 회로 요구사항으로 바꾸기
- 케이스 스터디: 증상 → 원인 후보 → 확인 절차 → 대책 (예: 특정 뱅크 읽기 페일, 리텐션 불량, tRCD 마진 부족, 고온 코너 페일)
- 설계 리뷰 모의: Agent가 리뷰어 역할로 질문하고 답변을 평가
- 문서 작성 훈련: 시뮬레이션 리포트, 설계 리뷰 자료를 양식에 맞춰 작성하면 피드백

### 3.2 샘플 학습 자료(코퍼스) 작성 지침
`docs_corpus/`에 Markdown으로 직접 작성한다. 공개 지식 수준으로만 쓰고, 정확하지 않은 내용은 넣지 않는다.
- 용어집: 40개 이상 (각 용어에 개념 태그, 난이도, 관련 Flow 단계 표기)
- 설계 Flow 단계별 문서: 7편 (Level 2의 7단계)
- 타이밍 파라미터 문서: 파라미터별 정의, 결정 요인, 관련 회로
- 케이스 스터디: 5편 이상
- 자주 하는 실수와 FAQ
- 실습용 에러 FAQ (ngspice, iverilog 에러 메시지 해설)
- 모든 문서 상단에 frontmatter: `title`, `level`, `concepts`(태그 목록), `flow_stage`

## 4. 기능 명세

### F1. 개념 Q&A
- 질문 → 수준 선택(입문/중급) → 코퍼스 검색 → 답변
- 답변 형식 고정: 한 줄 정의 → 비유 또는 그림 설명 → 실제 회로/동작 예시 → 관련 Flow 단계 → 출처
- 검색 유사도가 `config.yaml`의 임계값보다 낮으면 답변하지 않고 "문서 근거 없음 / 멘토 확인 필요"로 표시하고 멘토 큐에 저장
- "비유로 설명해줘", "수식으로 설명해줘" 같은 설명 방식 요청을 지원

### F2. 설계 Flow 내비게이터
- 7단계 Flow를 화면에 시각화(가로 단계 바 또는 다이어그램)
- 단계를 클릭하면 목적, 역할, 툴, 산출물, 관련 문서, 관련 퀴즈를 보여줌
- "내 업무는 어느 단계?" 기능: 직무를 입력하면 해당 단계와 앞뒤 단계와의 관계를 설명
- Level 3의 파라미터-회로 매핑 표도 여기서 열람 가능

### F3. 퀴즈·복습
- 개념 태그 또는 Flow 단계를 선택하면 객관식 5문제 생성
- LLM이 JSON(question, choices 4개, answer, explanation, concept)으로 생성하고 pydantic으로 검증. 검증 실패 시 재생성
- 채점 후 해설 표시, 틀린 개념은 SQLite에 저장
- 간격 반복: 틀린 개념은 1일, 3일, 7일 뒤 복습 퀴즈로 다시 출제

### F4. 실습 튜터 (두 트랙)
**(a) 회로 트랙 — ngspice**
- 과제: 비트라인 센싱(셀 캡–비트라인 캡 차지 셰어링), 센스앰프 동작, 프리차지
- 학습자가 셀 캡, 비트라인 캡, 센스앰프 트랜지스터 크기 등을 바꿔서 실행
- 결과 파형을 CSV로 받아 차트로 표시하고, 센싱 마진 변화를 Agent가 해석
- 넷리스트 템플릿과 파라미터 입력 UI 제공

**(b) 디지털 트랙 — iverilog**
- 과제 3개: 리프레시 카운터, 커맨드 디코더(ACT/RD/WR/PRE 디코딩), 간단한 해밍 ECC 인코더/디코더
- 각 과제는 문제 설명 + 뼈대 코드 + 채점용 테스트벤치로 구성
- 채점은 테스트벤치 결과로 하고 LLM은 채점하지 않는다
- 실패 시 힌트 3단계: 1단계 문제 위치만 → 2단계 원인 설명 → 3단계 수정 예시

**공통 안전장치**
- 임시 디렉터리에서 실행, 실행 시간 제한 10초, 출력 크기 제한
- `$system` 등 외부 실행 구문, 파일 시스템 접근 구문은 실행 전 차단
- 시뮬레이터가 설치되어 있지 않으면 앱이 죽지 않고 설치 안내를 표시

### F5. 실무 적응 트랙
- **스펙 해석 훈련:** JEDEC 스타일의 타이밍 표/다이어그램을 제시하고 "이 조건을 만족하려면 어느 회로에 어떤 요구가 생기는가"를 묻고 답변 평가
- **케이스 스터디:** 증상 제시 → 학습자가 원인 후보와 확인 절차를 작성 → 모범 답안과 비교 피드백
- **설계 리뷰 모의:** 학습자가 설계 내용을 설명하면 Agent가 리뷰어 역할로 질문 3~5개를 던지고 답변을 평가
- **문서 작성 훈련:** 시뮬레이션 리포트 양식(목적, 조건, 결과, 마진, 결론)에 맞춰 작성하면 누락·논리 오류 피드백

### F6. 학습 로드맵
- 직무 선택(회로설계 / 레이아웃 / 검증 / 제품엔지니어링) + 진단 퀴즈 10문항
- 6주 기본 커리큘럼을 YAML 템플릿으로 두고, 진단 결과로 약한 개념을 앞쪽 주차에 배치하는 방식으로 조정. LLM이 커리큘럼을 매번 새로 만들지 않는다.

### F7. 에러 로그 해석
- ngspice, iverilog 로그를 붙여넣으면 에러/경고 라인을 정규식으로 추출하고 줄별로 의미와 확인 포인트 설명
- 에러 FAQ 문서를 검색 근거로 사용

### F8. 대시보드 및 멘토 큐
- **학습자 탭:** 진도율, Flow 단계별·개념별 정답률 차트, 복습 예정 개념, 실습 완료 현황
- **멘토 탭:** Agent가 답하지 못한 질문 목록과 답변 입력칸. 멘토가 답변하면 `docs_corpus/mentor_answers/`에 저장하고 RAG 인덱스에 즉시 반영 (쓸수록 똑똑해지는 구조)

## 5. 시스템 구성

- **언어:** Python 3.11+
- **UI:** Streamlit, 사이드바 메뉴로 기능별 페이지 구분
- **LLM:** OpenAI API. `llm/` 모듈에 provider 인터페이스로 추상화하고, `config.yaml`의 `provider`, `model` 값만 바꾸면 사내 LLM 엔드포인트로 교체 가능하게 한다. 초기 모델명은 현재 사용 가능한 비용 효율적인 모델로 설정하고 config에서 변경 가능하게 둔다.
- **임베딩:** OpenAI 임베딩을 기본으로 하되, 로컬 임베딩(sentence-transformers)으로 교체 가능한 옵션 제공
- **RAG:** ChromaDB(로컬), 문서 로더(Markdown, PDF, DOCX), frontmatter 메타데이터 필터링
- **학습자 DB:** SQLite (프로필, 진도, 퀴즈 이력, 취약 개념, 실습 이력, 멘토 질문)
- **시뮬레이터:** ngspice, Icarus Verilog(iverilog/vvp) — 설치 여부 자동 확인
- **테스트:** pytest. 시뮬레이터 없는 환경에서도 통과하도록 시뮬레이터 의존 테스트는 skip 처리

## 6. API 키 및 환경 설정 (필수 산출물)

- `.env.example`: `OPENAI_API_KEY=`, `OPENAI_MODEL=`, `EMBEDDING_PROVIDER=` 등 필요한 항목을 빈 값으로 나열
- `.env`는 `.gitignore`에 반드시 포함
- `NOTE_API_KEY.md` 작성 (한국어):
  - 키를 어디서 발급받는지
  - `.env` 파일을 만들고 어느 줄에 붙여넣는지 (복사해서 쓸 수 있는 예시 포함)
  - 키가 정상 동작하는지 확인하는 방법 (`python -m llm.check` 같은 확인 스크립트 제공)
  - 주의사항: 키를 코드나 git에 넣지 말 것, 공유 금지, 사용량 확인 방법
  - 나중에 사내 LLM으로 전환할 때 바꿔야 할 항목 (`config.yaml`의 provider/endpoint)
  - 이 파일에 실제 키를 적는 곳은 없어야 한다
- 키가 없거나 잘못된 경우 앱이 죽지 않고 화면에 설정 안내를 표시한다

## 7. 구현 단계 (Phase)

각 Phase가 끝날 때마다 앱이 실행 가능한 상태여야 하고 테스트가 통과해야 한다.

- **Phase 0 — 계획 및 CLAUDE.md:** 이 제안서를 요약해 `CLAUDE.md`(프로젝트 개요, 원칙, 구조, 진행 현황 섹션 포함)를 작성한다. 이후 Phase마다 CLAUDE.md의 진행 현황을 갱신한다.
- **Phase 1 — 뼈대와 환경:** 디렉터리 구조, `requirements.txt`, `config.yaml`, `.env.example`, `NOTE_API_KEY.md`, 키 확인 스크립트, LLM 추상화, 기본 채팅 화면.
- **Phase 2 — 학습 자료와 Q&A:** 3.2의 코퍼스 작성, RAG 인덱싱, F1 개념 Q&A, F2 Flow 내비게이터.

- **Phase 4 — 실습 튜터:** F4. iverilog 디지털 트랙을 먼저 완성한 뒤 ngspice 회로 트랙 구현. 샌드박스와 안전장치 포함.

## 8. 개발 원칙

- **정확성 우선:** 교육용이므로 틀린 설명이 가장 치명적이다. 코퍼스 근거가 없으면 답하지 않는다. 코퍼스를 작성할 때도 확신이 없는 수치나 설명은 넣지 않는다.
- **보안:** 실제 설계 데이터·공정 파라미터는 절대 코퍼스에 넣지 않는다. 비밀정보는 코드에 하드코딩하지 않는다. LLM 호출 외에 사용자 입력을 외부로 보내는 코드를 넣지 않는다.
- **교육적 설계:** 정답을 바로 주기보다 힌트로 사고를 유도한다.
- **언어:** UI와 설명은 한국어, 기술 용어는 영문 병기. 예: 센스앰프(sense amplifier), 셋업 타임(setup time)
- **교체 가능성:** LLM, 임베딩, 코퍼스는 설정만 바꿔 교체할 수 있어야 한다.
- **작업 습관:** 기능 하나가 끝날 때마다 git commit. 파일 하나에 너무 많은 기능을 넣지 않는다.

## 9. 시연 시나리오 (최종 목표)

1. Flow 내비게이터에서 "회로 설계" 단계 클릭 → 코어/주변/디지털 블록 설명과 센스앰프 관련 문서 링크

4. ngspice 실습: 셀 캡을 줄이면 센싱 마진이 어떻게 변하는지 파형 차트로 확인하고 Agent 해석

## 추가 합의 사항 (2026-09-28, 계획 검토 시)

1. `core/services.py`: DB 연결, LLM provider, ChromaDB 클라이언트를 `st.cache_resource`로 한 번만 생성하고 모든 페이지가 여기서 가져다 쓴다.
2. `prompts/`: LLM 프롬프트 템플릿을 코드에 박지 않고 텍스트 파일로 분리한다.
3. `tutor/schemas.py`: `chat_json`에 쓰는 pydantic 모델(퀴즈, 케이스 평가, 리뷰 질문 등)을 한 곳에 모은다.
4. `sim/assignments/`를 `verilog/`, `spice/`로 나누고 과제마다 `meta.yaml`(id, 제목, 난이도, 개념 태그, 힌트 3단계)을 두어 Lab 페이지가 목록을 자동 생성한다.
5. 로드맵용 진단 퀴즈 10문항은 LLM 생성이 아니라 `curriculum/diagnostic.yaml` 고정 문항으로 한다.
6. 학습자 식별은 사이드바에서 이름을 입력하는 방식으로 하고 `db/repo.py`의 프로필과 연결한다.
7. `python -m rag.index --rebuild` 명령을 만들고, ChromaDB 폴더와 SQLite 파일은 `.gitignore`에 추가한다.
8. 모델 선택은 `.env`에서 끝낸다: `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OPENAI_MODEL`. `OPENAI_MODEL`이 비어 있으면 엔드포인트의 모델 목록을 조회해 `config.yaml`의 선호 순서에서 사용 가능한 첫 모델을 자동 선택한다(키만 바꿔도 알아서 바뀜).
9. 기본값으로 진행: OpenAI SDK 사용(`base_url` 교체), 시뮬레이터는 사용자가 설치, 로컬 임베딩은 별도 requirements로 분리, 코퍼스 수치는 "규격 참조" 수준, JEDEC 표는 자체 제작, NAND는 개념·파라미터 문서까지만(실습 없음).
